Flutter Developer Interview Guide

Flutter Developer — Hard Interview Questions

66 practical Flutter interview questions with simple answers and real-world examples.

Focus on explaining your thinking instead of memorizing definitions.

1. Flutter Fundamentals

HARD 1. What actually happens when a Flutter widget rebuilds?

Simple Answer:

When a widget rebuilds, Flutter calls its build() method again and creates a new widget configuration.

Flutter then compares the new widget configuration with the existing element tree and updates only the required parts.

Example:

If a counter value changes, Flutter does not recreate the entire application. It rebuilds the widgets affected by that state change.

HARD 2. Explain Widget, Element and RenderObject.

Simple Answer:

A Widget is the configuration or description of what the UI should look like.

An Element represents the widget's position in the widget tree and manages its relationship with the tree.

A RenderObject handles layout, painting and hit testing.

Easy way to remember:

Widget → What the UI should be.

Element → Where the widget lives.

RenderObject → How it gets laid out and painted.

HARD 3. What is BuildContext?

Simple Answer:

BuildContext represents the location of a widget inside the widget tree.

It allows us to access things such as Theme, Navigator, MediaQuery and inherited widgets.

Example: 

Navigator.of(context).push(
  MaterialPageRoute(
    builder: (_) => const HomePage(),
  ),
);

HARD 4. Why should expensive operations not be placed inside build()?

Simple Answer:

The build method can run many times. If I perform expensive operations inside it, the UI can become slow.

Example:

I should not make an API request or perform heavy JSON processing directly inside build().

HARD 5. Why use const widgets?

Simple Answer:

Const widgets are compile-time constants. Flutter can reuse them when their values don't change. This can reduce unnecessary work during rebuilds. 


const Text("Hello");

HARD 6. StatelessWidget vs StatefulWidget?

Simple Answer:

A StatelessWidget does not maintain mutable local state.

A StatefulWidget has a State object that can change during the lifetime of the widget.

Example:

A static title can use StatelessWidget. A counter that changes can use StatefulWidget.

HARD 7. Why initState() and dispose()?

Simple Answer:

initState() is used for initialization when the State object is created.

dispose() is used to clean up resources when the widget is removed. 


@override
void initState() {
  super.initState();

  controller = TextEditingController();
}

@override
void dispose() {
  controller.dispose();

  super.dispose();
}

HARD 8. What are Keys and when do you use them?

Simple Answer:

Keys help Flutter identify widgets when the widget tree changes.

They are especially useful when working with dynamic lists or when preserving the state of widgets after reordering. 


ListTile(
  key: ValueKey(user.id),
  title: Text(user.name),
);

2. Dart & Async

HARD 9. Future vs Stream vs async/await?

Simple Answer:

A Future represents one value that will be available later.

A Stream represents multiple values over time.

async/await makes asynchronous Future-based code easier to read. 


Future<User> getUser();

Stream<Message> messages();

final user = await getUser();

HARD 10. Is Dart single-threaded?

Simple Answer:

Dart code normally runs on a single isolate with an event loop.

Asynchronous operations allow the application to continue while waiting for things such as network requests.

For CPU-heavy work, Dart provides isolates.

HARD 11. When would you use an isolate?

Simple Answer:

I would use an isolate for CPU-intensive operations that could block the main UI isolate.

Examples:
  • Large JSON parsing
  • Image processing
  • Complex calculations
  • Large data processing

HARD 12. final vs const?

Simple Answer:

final means the value can be assigned only once at runtime.

const means the value is a compile-time constant. 


final name = getName();

const age = 25;

HARD 13. What is null safety?

Simple Answer:

Null safety helps prevent null reference errors by making nullable and non-nullable types explicit. 


String name = "Praveen";

String? nickname;

if (nickname != null) {
  print(nickname);
}

3. State Management

HARD 14. Why do we need state management?

Simple Answer:

State management helps us manage and share application state in a predictable way.

It also keeps business logic separate from UI code.

For example, login state may be needed by the home screen, profile screen and settings screen.

HARD 15. Bloc vs Cubit?

Simple Answer:

Cubit is simpler and directly exposes methods that emit new states.

Bloc uses events and converts those events into states. 


class CounterCubit extends Cubit<int> {

  CounterCubit() : super(0);

  void increment() {
    emit(state + 1);
  }
}

I normally choose Cubit when the state flow is simple and Bloc when event-driven logic becomes more complex.

HARD 16. How would you manage a shopping cart across multiple screens?

Simple Answer:

I would keep the cart state outside individual screens, using something like Cubit, Bloc or another state management solution.

The cart would expose operations such as add, remove, increase quantity and decrease quantity.

The product screen adds an item to the cart. The cart screen observes the same state. The checkout screen also reads that state.

HARD 17. How do you prevent unnecessary rebuilds with Bloc?

Simple Answer:

I can use BlocBuilder carefully and use buildWhen or BlocSelector when only a specific part of the state is required. 


BlocSelector<CartCubit, CartState, int>(
  selector: (state) => state.itemCount,
  builder: (context, count) {
    return Text('$count');
  },
)

HARD 18. What happens if two updates modify the same state at the same time?

Simple Answer:

I need to make sure state updates are handled predictably. I avoid directly modifying mutable state and create new state objects for each update.

For asynchronous operations, I also consider whether the operations should run sequentially, concurrently or cancel previous requests.

4. Architecture & Clean Code

HARD 19. Explain Clean Architecture.

Simple Answer:

Clean Architecture separates the application into different responsibilities.

  • Presentation
  • Domain
  • Data

The main goal is to keep business logic independent from UI and external systems.

For example:

UI → Cubit → Use Case → Repository → API

HARD 20. Why do we use a Repository?

Simple Answer:

A repository hides where the data comes from.

The rest of the application doesn't need to know whether the data came from an API, database or cache. 


class UserRepository {

  Future<User> getUser() async {
    // API or database
  }
}

HARD 21. Why should business logic not be inside widgets?

Simple Answer:

If business logic is inside widgets, the code becomes harder to test, reuse and maintain.

I prefer keeping business logic inside Cubit, Bloc, use cases or services depending on the architecture.

HARD 22. What is Dependency Injection?

Simple Answer:

Dependency Injection means providing an object with the dependencies it needs instead of creating those dependencies inside the object. 


class UserService {

  final UserRepository repository;

  UserService(this.repository);
}

HARD 23. MVC vs Clean Architecture?

Simple Answer:

MVC separates code into Model, View and Controller.

Clean Architecture usually separates presentation, domain and data responsibilities with stronger dependency boundaries.

For larger applications, Clean Architecture can make maintenance and testing easier.

5. REST API & Networking

HARD 24. The API works in Postman but not in Flutter. How do you debug it?

Simple Answer:

First I compare the Flutter request with the Postman request.

  • URL
  • HTTP method
  • Headers
  • Authorization
  • Request body
  • Content-Type

Then I check the actual request and response using logs or an HTTP interceptor.

HARD 25. Explain common HTTP status codes.

  • 200 — Success
  • 201 — Created
  • 400 — Bad request
  • 401 — Unauthorized
  • 403 — Forbidden
  • 404 — Not found
  • 500 — Server error

HARD 26. PUT vs PATCH?

Simple Answer:

PUT is generally used to replace the complete resource.

PATCH is generally used to partially update a resource. 


PUT /users/10

{
  "name": "Praveen",
  "email": "user@example.com"
}


PATCH /users/10

{
  "name": "Praveen Kumar"
}

HARD 27. How would you implement pagination?

Simple Answer:

I keep track of the current page and whether more data is available.

When the user approaches the bottom of the list, I request the next page and append the result to the existing list. 


GET /products?page=1&limit=20

GET /products?page=2&limit=20

HARD 28. What would you do if an API request times out?

Simple Answer:

I would show an appropriate error message instead of leaving the user waiting indefinitely.

Depending on the API, I could also retry the request with a reasonable limit and backoff.

For a payment request, I would be especially careful about retrying because repeating the request could cause duplicate transactions.

HARD 29. How would you handle API errors consistently?

Simple Answer:

I would create a common error model or exception structure and map network errors, server errors, validation errors and timeouts into it. 


NetworkException
ServerException
TimeoutException
ValidationException
UnauthorizedException

6. Authentication & Security

HARD 30. Explain a JWT login flow.

Simple Answer:
  1. User enters username and password.
  2. Flutter sends them to the login API.
  3. Server validates the credentials.
  4. Server returns an access token.
  5. Flutter stores the token securely.
  6. Flutter sends the token with authenticated requests.

HARD 31. What happens when the access token expires?

Simple Answer:

If a refresh token is available, the application can request a new access token and retry the original request.

If refresh fails, I would clear the authentication state and send the user back to login.

HARD 32. Where should authentication tokens be stored?

Simple Answer:

Sensitive tokens should be stored using secure platform storage rather than plain SharedPreferences.

For Flutter, a secure storage solution can use Android Keystore and iOS Keychain.

HARD 33. How would you protect authenticated routes?

Simple Answer:

I would keep authentication state in a central place and check it before allowing access to protected screens.

With GoRouter, for example, I can use redirects based on authentication state.

7. Performance

HARD 34. You have a list containing 50,000 products. How would you handle it?

Simple Answer:

I would not load all 50,000 products into memory at once.

I would use server-side pagination and Flutter's lazy list widgets such as ListView.builder.

For example, load 20 or 50 products at a time and request the next page when the user scrolls near the bottom.

HARD 35. Images are loading very slowly. What would you check?

Simple Answer:
  • Image file size
  • Image dimensions
  • Network speed
  • Caching
  • Image format
  • Thumbnail usage

For a product list, I would use smaller thumbnail images instead of loading the full-resolution image for every item.

HARD 36. How would you investigate Flutter performance issues?

Simple Answer:

I would reproduce the issue and use Flutter DevTools to inspect CPU usage, memory, widget rebuilds and frame rendering.

I would identify the actual bottleneck before optimizing.

HARD 37. How can you reduce unnecessary widget rebuilds?

Simple Answer:
  • Use const widgets where possible.
  • Split large widgets into smaller widgets.
  • Use BlocSelector or buildWhen.
  • Avoid putting unrelated state in the same widget.
  • Use lazy lists for large collections.

8. Debugging & Production Problems

HARD 38. The app crashes only in production. How would you debug it?

Simple Answer:

First I would check crash reporting tools and production logs to get the stack trace.

Then I would identify the affected version, device, OS version and reproduction conditions.

After fixing it, I would test the fix and release a new version.

HARD 39. Android works but iOS fails. What would you check?

Simple Answer:
  • iOS permissions
  • Info.plist
  • Pod dependencies
  • Signing and provisioning
  • Platform-specific code
  • iOS API restrictions

HARD 40. A button triggers the API twice. How would you investigate?

Simple Answer:

I would first check whether the button callback is firing twice or whether the API layer is retrying the request.

I would also disable the button while the request is in progress if duplicate submissions are not allowed. 


if (state.isSubmitting) {
  return;
}

submit();

HARD 41. Memory usage keeps increasing. What could be the reason?

Simple Answer:

It could be caused by resources that are not being released.

  • Controllers not disposed
  • Streams not cancelled
  • Listeners not removed
  • Large objects kept in memory
  • Image memory

9. Local Storage & Offline Support

HARD 42. SharedPreferences vs Hive vs SQLite?

Simple Answer:

SharedPreferences is suitable for small key-value data.

Hive is useful for local NoSQL-style storage.

SQLite is suitable for structured relational data and more complex queries.

A theme preference can use SharedPreferences. A cached object can use Hive. Complex relational offline data can use SQLite.

HARD 43. How would you implement offline support?

Simple Answer:

I would cache important API data locally and display it when the network is unavailable.

When the network becomes available again, I would refresh the data from the server.

HARD 44. What if the user edits data while offline?

Simple Answer:

I would save the change locally and mark it as pending.

When the network becomes available, the application can sync the pending changes with the server.

For example:


Local database

Task
------
id
title
syncStatus = pending

10. Testing

HARD 45. Unit Test vs Widget Test vs Integration Test?

Simple Answer:
  • Unit test: Tests a small piece of logic.
  • Widget test: Tests a Flutter widget and its interaction.
  • Integration test: Tests the application flow across multiple parts.

HARD 46. How would you test a login feature?

Simple Answer:
  • Valid credentials
  • Invalid credentials
  • Empty fields
  • Network failure
  • Server error
  • Loading state
  • Successful navigation

HARD 47. How would you test a Cubit?

Simple Answer:

I would verify that calling a method produces the expected sequence of states.

11. Android & iOS

HARD 48. APK vs AAB?

Simple Answer:

APK is an Android application package that can be installed directly on a device.

AAB is Android App Bundle. Google Play uses it to generate optimized APKs for different devices.

HARD 49. minSdk vs targetSdk?

Simple Answer:

minSdk defines the minimum Android version supported by the application.

targetSdk indicates the Android version the application is designed and tested against.

HARD 50. Explain iOS certificates and provisioning profiles.

Simple Answer:

Certificates identify and sign the application.

Provisioning profiles define which application identifier, devices and entitlements can be used with that signing setup.

HARD 51. A Flutter plugin works on Android but fails on iOS. What do you check?

Simple Answer:
  • Whether the plugin supports iOS
  • iOS permissions
  • Info.plist configuration
  • Pod installation
  • Minimum iOS version
  • Native iOS configuration
  • Signing capabilities

12. Hard Real-World Feature Design

HARD 52. Design a shopping cart feature.

Simple Answer:

First I would understand the requirements. Then I would define the data model and state.

The cart state would contain products, quantities, subtotal, discounts and total. 


Cart
 ├── Product
 ├── Quantity
 ├── Price
 ├── Discount
 └── Total

I would keep cart logic inside Cubit/Bloc rather than directly inside the UI.

HARD 53. How would you design a chat application?

Simple Answer:

For real-time messaging, I would consider WebSockets.

I would maintain message state locally and update it when new messages arrive.

I would also handle reconnects, offline messages and message delivery status. 


User

Flutter
 ↓

HARD 54. What edge cases would you consider for a booking feature?

Simple Answer:
  • Slot already booked
  • Network failure
  • Payment failure
  • Double tap
  • Server timeout
  • Provider unavailable
  • Booking cancellation
  • Time zone issues

HARD 55. Payment succeeded but booking failed. What would you do?

Simple Answer:

This is a transaction consistency problem.

I would not simply tell the user that payment failed. I would check the payment status and booking status from the server.

The backend should ideally provide an idempotent and reliable workflow for payment and booking.

HARD 56. How would you prevent double booking?

Simple Answer:

The frontend can disable duplicate submissions, but the backend must be the final authority.

The server should atomically verify and reserve the slot.

Two users may click the same slot at almost the same time. The backend must ensure only one booking succeeds.

HARD 57. How would you design a notification system?

Simple Answer:

I would use push notifications for events that need to reach the user when the application is in the background.

I would handle foreground, background and terminated states.

For example, a booking confirmation could trigger a push notification containing the booking ID.

HARD 58. How would you design location tracking?

Simple Answer:

I would request the required location permissions and listen for location updates.

I would avoid sending every GPS update to the server. Instead, I would use an appropriate distance or time threshold.

For vehicle tracking, the application could send an update when the vehicle moves a certain distance or after a reasonable interval.

HARD 59. How should the app behave with a poor network?

Simple Answer:
  • Show loading state
  • Use cached data where possible
  • Set reasonable timeouts
  • Retry appropriate requests
  • Show clear error messages
  • Prevent duplicate submissions

HARD 60. What if the user closes the app immediately after pressing Submit?

Simple Answer:

I would not rely only on the Flutter UI to determine whether the operation succeeded.

The backend should process the request reliably and the operation should be idempotent when necessary.

When the user opens the application again, I can fetch the latest server state.

13. Behavioral & Experience Questions

BEHAVIORAL 61. Tell me about a difficult bug you solved.

Use STAR:

Situation: Explain what was happening.

Task: Explain what you were responsible for.

Action: Explain how you investigated and fixed it.

Result: Explain what improved after the fix.

Sample answer:

"In one of my projects, we had an issue where a feature was working correctly during development but had problems in production. I first reproduced the issue and checked the logs and API responses. I found that the problem was related to how the production data was handled. I fixed the issue, tested different cases and released the fix. After the release, the issue was resolved."

BEHAVIORAL 62. Tell me about a mistake you made.

Simple Answer:

Choose a real mistake that does not make you look careless, then explain what you learned.

Sample answer:

"Earlier in my career, I sometimes tried to solve a problem completely by myself before asking for help. I realized that this could take more time than necessary. Now I first investigate the issue myself, but if I am blocked, I communicate with the team earlier."

BEHAVIORAL 63. What is your weakness?

Good approach:

Choose a genuine weakness and explain how you are improving it.

Sample answer:

"One area I am working on is that sometimes I spend too much time trying to solve a problem on my own. I have learned to set a reasonable time limit and ask for help when I am blocked. This has helped me work more efficiently."

BEHAVIORAL 64. Why should we hire you?

Simple Answer:

"I have practical experience building Flutter applications and working with APIs, state management and production issues. I am comfortable learning new technologies and debugging problems. I also focus on writing maintainable code and delivering features reliably."

BEHAVIORAL 65. Why are you looking for a new opportunity?

Simple Answer:

"At this stage of my career, I am looking for an opportunity where I can apply my existing experience, take on more challenging problems and continue growing as a software developer."

Interview Tip:

Keep the answer positive. Avoid criticizing your previous company.

BEHAVIORAL 66. What if you don't know the answer to an interview question?

Simple Answer:

"I haven't worked with that directly yet, so I don't want to give you an incorrect answer. But I would approach it by first understanding the requirement, checking the relevant documentation and testing a small example."

Important:

Don't try to bluff. Interviewers usually care more about your problem-solving approach than pretending to know everything.
